# Lift Lab

Eigenständige Trainings-App (PWA, nur lokal, Deutsch) mit regelbasierter Progression. Eigenentwicklung: keine Übernahme von Code, Assets, Namen oder Texten anderer Apps. **Ausnahme (bewusste Entscheidung):** Übungsbilder und ausgewählte Texte aus `free-exercise-db-with-videos` (MIT), siehe `THIRD_PARTY.md`, `docs/PLAN-3.md`. Ausführliche Planung: `docs/PLAN-1.md` (Grundplan) und `docs/PLAN-2.md` (Erweiterung: Warm-ups, Timer, Logger, Dashboard), `docs/PLAN-5.md` (geplant: Gerätegewichte, Wizard-Überarbeitung), `docs/PLAN-6.md` (Abgleich mit MacroFactor-Doku, **Checkliste mit Status: vor jeder Aufgabe lesen, Aufgabe abhaken**).

## Befehle
```bash
npm run dev        # Dev-Server (Port 5173, siehe .claude/launch.json)
npm test           # Vitest, alle Engine-/Daten-Tests
npm run typecheck  # tsc -b
npm run build      # tsc -b + Vite-Build + PWA
```
Vor jedem Abschluss: `npm run typecheck && npm test && npm run build`.

## Stack
Vite 8, React 19, TypeScript (strict, `erasableSyntaxOnly`: keine Enums/Parameter-Properties), Tailwind CSS v4, Dexie (IndexedDB), react-router-dom (HashRouter), eigene SVG-Diagramme (kein Chart-Paket), vite-plugin-pwa, Vitest.

## Struktur (`src/`)
- `types.ts`: alle Domänentypen (Program, Session, ProgramConfig, Settings …)
- `data/`: `muscles.ts` (22 Muskelgruppen, einzige Quelle; Migration alter IDs in `muscleMigration.ts`), `exercises.ts` (Übungen als Tupel-Zeilen + Cardio)
- `engine/`: **reine Funktionen ohne UI/DB**, vollständig getestet
  - `progression.ts` (e1RM, Double Progression, Plateau), `periodization.ts` (Rep-Schemata, Deload)
  - `planGenerator.ts` (Wizard-Config → Programm), `swap.ts`, `weekCycle.ts` (Wochenreset), `weekProgress.ts`, `stats.ts`
  - `bodyweight.ts` (Körpergewichtsanteil), `setTypes.ts` (Drop/Myo-Segmente), `superset.ts` (Supersätze)
  - `warmup.ts` (Aufwärmrampe), `rest.ts` (Pausen-Kategorien/Defaults), `plannedDay.ts` (geteilte Tagesberechnung für Vorschau + Logger), `workoutClock.ts` (Timer mit Pausen)
- `db/db.ts`: Dexie-Schema, Hooks (`useSessions` …), Backup Export/Import, Gewichts-Import (Apple-Health-XML/CSV)
- `engine/trainingImport.ts` + `data/importAliases.ts`: Import eines Trainingsverlaufs (CSV, eine Zeile pro Satz) als Sessions mit `programId: null`, `week: 0`, `dayIndex: -1`. Zuordnung über Alias-Tabelle (englische Namen → IDs), Rest wählt der Nutzer in der Vorschau (`features/more/TrainingImport.tsx`). Übungen, die am selben Tag schon geloggt sind, werden übersprungen (wiederholter Import unschädlich).
- `features/`: `wizard`, `workouts` (Wochenplan, Vorschau, Logger mit Timer/Satztabelle/Numpad/Info-Sheet), `dashboard`, `stats`, `body` (Gewicht, Maße), `more`
- `data/media/`: `map.json` (App-ID → Repo-Slug), `manifest.json` (vorhandene Poster, erzeugt von `scripts/build-media.mjs`), `index.ts` (`posterUrl`). Bilder in `public/exercise-media/poster/`. Videos: nur Idee, `docs/IDEAS-VIDEOS.md`.
- `data/instructions.ts` (+ `data/instr/*`): eigene Anleitungen pro Übungs-ID (Info-Sheet lädt sie per dynamischem Import; Seiten in `App.tsx` per `React.lazy`). `components/MuscleFigure.tsx`: eigene SVG-Muskelfigur (kein Fremd-Asset).
- `components/ui.tsx`: gemeinsame UI-Bausteine; `utils/`: Datum und Einheiten

## Konventionen und Invarianten
- **Speicherung immer metrisch** (kg, cm, km). Umrechnung nur bei Anzeige/Eingabe über `utils/units.ts`.
- Datumsangaben sind lokale Strings `yyyy-mm-dd` (`utils/dates.ts`), keine UTC-ISO-Strings.
- Neue Logik gehört in `engine/` (rein, mit Test in `engine.test.ts`), nicht in Komponenten.
- Muskel-Sets/Volumen: primäre Muskeln voll, sekundäre mit `SECONDARY_WEIGHT` (0,5). Cardio zählt nie mit.
- **Je Seite** (`isPerSide`, `engine/stats.ts`): liest `Exercise.load` (`'single' | 'perSide'`, bei jeder Kurzhantel-/Kettlebell-Übung explizit in `data/exercises.ts`). Gewicht/Wdh. werden je Seite gespeichert, Volumen zählt × 2 (`volumeFactor`); 1RM/Heaviest bleiben je Gerät. Ohne Feld (eigene Übungen) gilt Kurzhantel = je Seite.
- **Generator**: Zeitbudget (`SESSION_SET_CAP`) gilt für die Spitzenwoche (`PEAK_SETS_FACTOR`). Zeitbasierte Übungen (`TIME_BASED`) nur über `config.includeExercises`, Band nur bei gewähltem Band-Equipment.
- **Warm-up**: `engine/warmup.ts`. Modus Smart (Schwere + Frische des Muskels), Scheme (5 Kategorie-Schemata in `Settings.warmupSchemes`) oder aus; pro Übung überschreibbar über `kv['exerciseOverrides']` (`warmupMode`, `warmupScheme`, `note`). Programm-Notizen in `kv['programNotes']`, Session-Notizen in `Session.notes`.
- **Körpergewicht/Assistiert**: Sätze mit `weight 0` zählen für Sätze/Wdh. (`stats.ts` `work()`), nicht für 1RM/Volumen (`loaded()`); Progression dort rein über Wiederholungen, solange kein Körpergewichtsanteil greift.
- **Körpergewichtsanteil** (`engine/bodyweight.ts`): `Exercise.bodyweight` (0–1, `BODYWEIGHT_SHARE` in `data/exercises.ts`, nur Körpergewichtsübungen, Rumpf außer hängendem Beinheben nicht). Gespeichert wird nur das Zusatzgewicht; Last = Anteil × Körpergewicht (letzter Eintrag im Gewichtsverlauf bis zum Datum, `bodyweightAt`) + Zusatzgewicht. Progression (`suggestNext` `bodyLoad`/`lastBodyLoad`, `adaptNextSets` `bodyLoad`) rechnet mit der Gesamtlast und gibt Zusatzgewicht zurück; „Halten“ = gleiches Zusatzgewicht, Hysterese ≈ eine Wdh. (Last/30). Erstes Zusatzgewicht (Obergrenze ohne Zusatz erreicht): kleinste Stufe (`BODYWEIGHT_ADDED_START` bzw. Skala-Minimum), Wdh. aus dem e1RM bei Ziel-RIR statt Untergrenze. Statistiken über `useStatSessions` (`applyBodyweight`, nur Anzeige, nie speichern). Ohne Gewichtseintrag, bei assistierten und Zeitübungen bleibt alles wie zuvor. `Exercise.assisted` (Gewicht = Unterstützung): Progression senkt das Gewicht, keine 1RM-/Volumenwerte.
- **e1RM**: `progression.ts` `e1rm`/`weightForReps` (Epley, ab 12 effektiven Wdh. gedämpft, 1 Wdh. = Gewicht). Fehlendes RIR überall `FALLBACK_RIR` (2). Plateau-Erkennung nutzt `sessionPerformance` (ohne RIR-Korrektur), sonst wertet ein exakt befolgter Plan als Stillstand.
- **Zeitübungen**: `Exercise.metric === 'time'` (`TIME_BASED`): `reps` sind Sekunden, Range `TIME_RANGE`, Progression +`TIME_STEP` s, kein Aufwärmen, kein 1RM/Volumen (`noLoadStats` in `stats.ts`, gilt auch für assistiert).
- **Plateau**: `isStalled` startet nach einem e1RM-Abfall (> 2 %) neu, Deload-Einheiten sind ausgeschlossen (`deloadSessionOf`).
- **Folgesätze im Logger** (`adaptNextSets`): Satz nach Plan (±1 RIR, `ADAPT_DEAD_ZONE`) → unverändert. Sonst Gewicht **und** Wdh. aus dem abgehakten Satz (reine Epley-Umrechnung), `FATIGUE_REPS` (1) je Satz Abstand; Gewicht einmal für den nächsten Satz gewählt (±10 %), spätere Sätze verlieren nur Wdh. Ohne `planKg` (keine Historie) kalibriert der erste Satz (±20 %). Angepasste Zeilen bekommen neue `planKg/planReps`. Von Hand geänderte Zeilen (`manual`, Gewicht oder Wdh.) bleiben.
- **Zielwert / Weight Match** (`Settings.progressionTarget`, `weightMatch`, `expandRange`; App-Standard `mid`/an/an, Engine-Standard ohne Angabe `min`): `min` = klassische Double Progression. `mid` (`suggestMid`): Ziel-e1RM = schwächster Top-Satz + 1 Wdh. (mit dessen RIR, mehr nur bei Mehrleistung, max. `MAX_E1RM_JUMP`), Kandidaten = Stufen um das gehaltene Gewicht + Gewicht für die Mitte (`midOf`, abgerundet), Wdh. je Kandidat bei Ziel-RIR. Weight Match hält das Gewicht, solange die Wdh. im Bereich liegen, sonst Kandidat am nächsten an der Mitte. Ungedämpfter Epley in `suggestMid` (Dämpfung nur für 1RM). Plateau-Reset zielt bei `mid` auf die Mitte.
- **Equipment-Grenzen** (`suggestNext`, Obergrenze erreicht): trägt die nächste Stufe nach ungedämpftem Epley nicht einmal Untergrenze − 1 Wdh. bei Ziel-RIR, bleibt das Gewicht und die Wdh. steigen über die Obergrenze (`note: 'extend'`, `nextWeight`), höchstens bis Obergrenze + max(2, ⌈25 %⌉) (`EXTEND_REPS`); danach Sprung mit den machbaren Wdh. (`note: 'gap'`). Ende der Geräteliste: Gewicht halten, Wdh. bis zur erweiterten Grenze (`gap` ohne `nextWeight`). Hinweistext `features/workouts/progressionNote.ts` in Logger und Vorschau.
- **Trainingspause**: `detrainFactor(daysSince)` ab 21 Tagen (1,5 %/Woche über 2 Wochen, max. 15 %) deckelt `suggestNext`. `plannedDay` bekommt dafür `today`. Konstanten (Ermüdung, Pause) sind am Trainingsverlauf des Nutzers kalibriert (Backtest im Code-Kommentar).
- **Rep-Schemata**: `exerciseTargets` (Bereich + RIR je Übung/Woche, geteilt von Logger, Vorschau, Wizard). `rotating` = drei 3-Wdh.-Zonen um die Mitte des Basisbereichs (`zoneRange`), Zone = (Blockwoche + Position im Tag) mod 3, schwere Zone +1 RIR, Reserve sinkt über den Block nur um 1 und bleibt bei Verbundübungen ≥ 1, Deload mittlere Zone; Automatik-Empfehlung für Fortgeschrittene (außer Kraft). Letzte Arbeitswoche: `failureLastSet` → letzter Arbeitssatz RIR 0, `Row.failure` zeigt „+“.
- **Harter Satz zuerst** (`Settings.hardSetFirst`, Standard aus): `setRir(..., hardFirst)` erster Arbeitssatz Ziel − 1 (Verbund nicht unter 1, außer Ziel 0), übrige Ziel-RIR; Versagenssatz der letzten Arbeitswoche ist dann der erste (`failureSetIndex`, `PlannedView.failureIdx`).
- **Mehrere Programme**: `activateProgram` rekonstruiert den Wochenstand aus den Sessions. Der Wochenkalender zeigt nur Tage mit geloggten Workouts.
- **Aufwärmsätze** (`LoggedSet.warmup`) zählen nie in Volumen, Sets, e1RM, Progression oder Wochenfortschritt (Filter in `stats.ts` `work()`, `suggestNext`, `sessionE1rm`, `weekProgress`). Sie werden zur Laufzeit aus dem Arbeitsgewicht berechnet, nicht im Plan gespeichert. Abgehakte Aufwärmsätze klappt der Logger zu einer Sammelzeile ein (`Settings.hideDoneWarmups`, Standard an, `collapsedWarmups`); Zeile mit offenem Numpad bleibt sichtbar.
- **Satztypen** (`LoggedSet`): `failure` (RIR 0, Kürzel F), `segment: 'drop' | 'myo'` = Fortsetzung des Arbeitssatzes davor (Kürzel D/M, im Logger Zeilentyp `drop`/`myo`), `partial` = Teilwiederholungen (nur Protokoll). Segmente zählen für Wdh. und Volumen, nie als Satz, nie für 1RM/schwerstes Gewicht/Bestsatz, Progression, Vergleichszeile oder Wochenfortschritt (`stats.ts` `mainSets`/`loadedMain`, `previousSets`, `sessionE1rm`, `weekProgress`). Vorbelegung `nextSegment` (Drop −20 %, Myo ⅓ Wdh., `MYO_REST_SEC`).
- **Vorbelegung** (`Settings.prefillMode`, Standard `suggestion`): `last` belegt Arbeitssätze mit Gewicht/Wdh. (und Seiten) des gleichen Satzes der letzten Einheit (`engine/prefill.ts`), Plan-Werte für `adaptNextSets` = Vorbelegung; der Progressionsvorschlag steht dann als Zeile über der Tabelle.
- **Links/rechts getrennt** (`engine/sides.ts`): `Exercise.unilateral` (`UNILATERAL` in `data/exercises.ts`, wechselnde Ausfallschritte nicht) = Standard an, je Übung über `ExerciseOverride.sides` (Logger-Pill „Links/Rechts“). Ein Satz bleibt ein Satz: `LoggedSet.sides { l, r }`, `weight`/`reps`/`rir` oben = schwächere Seite (`weakerSide`, e1RM mit Körperlast, Zeitübungen Sekunden), damit Progression, 1RM und Plateau unverändert die schwächere Seite sehen. Volumen = Faktor × Summe beider Seiten (`setVolume`). Nur Arbeitssätze (keine Aufwärmsätze/Segmente). Logger: `Row.right`/`leftDone`, eine Seite abhaken startet `Settings.sideRest` (15 s, 0 = aus), beide Seiten = Satz erledigt; offene rechte Seite übernimmt Änderungen links; Ausschalten behält die schwächere Seite.
- **Supersätze**: `PlannedExercise.superset` (gleiche ID bei benachbarten Übungen, ID = erste Übungs-ID, `withLinks` normalisiert). Im Logger verbinden/lösen (gilt sofort für den Trainingstag im Programm). Nach einem Arbeitssatz `nextInSuperset`: nächste offene Übung der Runde ohne Pause, nach der letzten Pause und zurück.
- Das laufende Workout liegt in `kv['activeWorkout']` (Reload-fest, nicht im Backup). Timer ist zeitstempelbasiert (`workoutClock.ts`).
- Pausen-Defaults und Warm-up-/RIR-Regeln sind Heuristiken (Quellen im Code-Kommentar), Pausen in Einstellungen änderbar. Aufwärmpausen: `warmupRestBetween` (30 s) zwischen Aufwärmsätzen, `warmupRestLast` (90 s) nach dem letzten (`restSecondsFor(..., 'work' | 'warmup' | 'lastWarmup')`). Pausen-Timer: Uhr in der Logger-Kopfzeile (`RestTimer.tsx`), Menü mit ±15 s, Stopp, eigenen Timern.
- **Blocklänge**: `ProgramConfig.blockWeeks` (3–8, `BLOCK_WEEK_OPTIONS`, fehlt = 4, `blockWeeksOf`). `weekPlan` streckt den Verlauf (Rep-Shift gesamt 3, RIR −2, Spitzenphase = zweite Blockhälfte); bei 4 Wochen identisch zum alten Verlauf. `deloadFirst`: Deload ist Position 0 im Block, die Arbeitswochen folgen (`blockPosOf`, `weekInBlock(week, config)`, −1 = Deload).
- **Wochenziele** (`PlannedExercise.weeks`, `WeekTarget`): `b<Position im Block>` gilt in jedem Block (Wizard-Wochenkarten, Vorschau „In jedem Block“), `w<Programmwoche>` nur einmal (Vorschau „Nur diese Woche“, auch ohne Periodisierung über `neutralWeek`), `w` hat je Feld Vorrang (`weekOverride`). Überschreibt Sätze (`plannedSets`), Bereich/RIR (`exerciseTargets`), `skip` = Übung auslassen (`isSkipped`: Logger blendet aus, Vorschau dimmt, zählt nicht zum Wochenfortschritt und nicht für Supersätze). Bearbeiten über `features/workouts/WeekTargetSheet.tsx`, `setWeekTarget` entfernt leere Einträge. Tausch auf einen anderen Übungstyp verwirft die Wochenziele.
- **Nie empfehlen** (`ExerciseOverride.neverRecommend`, Schalter im Info-Sheet › Details): `recommendable` (`swap.ts`) filtert die Übung aus Generator und Tauschvorschlägen im Wizard; freie Auswahl und bestehende Pläne bleiben. Die Wizard-Vorschau wartet auf die geladenen Overrides.
- **Körperkarte** (`features/dashboard/BodyMap.tsx`: Dashboard-Bereich „Volumen“ mit Kachel `VolumeTile` (Ø 4 Wochen), Tipp öffnet Panel mit `BodyMap`): `weeklyMuscleSets` (Ø Arbeitssätze/Woche, rollierend 1/4/12 Wochen, sekundär `SECONDARY_WEIGHT`), Farbstufen `setTier` (< 4, 4–9, 10–20, > 20), Liste klappt je Muskel die Übungsbeiträge auf (`muscleContributions`, Summe = Muskelwert), „Verlauf ansehen“ führt zur Muskel-Statistik.
- **Wochenvolumen** (`volumeSplit` in `stats.ts`, Karte oben im Volumen-Panel, gleicher Zeitraum wie die Körperkarte): Ø kg/Woche getrennt nach Gewicht (gespeichertes Gewicht, `setVolume`) und Körpergewichtsanteil (`bodyLoadOf` × Wdh. × Faktor); bekommt gespeicherte Sessions, nicht `applyBodyweight`.
- **Scheibenrechner** (`engine/plates.ts` `platesFor`, `Settings.barWeight`/`plates` in kg, Einstellungen › Workouts › Langhantel): bei Langhantelübungen zeigt das Numpad im Gewichtsfeld die Scheiben pro Seite (schwerste zuerst), nicht ladbaren Rest bzw. „Leichter als die Stange“.
- Cardio wird nie vom Plan-Generator eingeplant, nur manuell hinzugefügt.
- **Workout überspringen** (`skipSlot`/`isSlotSkipped` in `weekCycle.ts`, `WeekState.skipped`): Slot gilt als erledigt ohne Einheit (keine Progression/Statistik), letzter offener Slot startet die nächste Woche; Vorschau „Überspringen“ / „Nicht mehr überspringen“ (nur aktives Programm), Wochenliste zeigt „Übersprungen“. `unmarkSlot` löscht die Markierung.
- Wochenzyklus: `Session.week` ist die Programmwoche. Sind alle 7 Slots erledigt, setzt `markSlot` zurück und zählt die Woche hoch. Die Wochenauswahl (`weekOptions`, `weekLabel` in `weekCycle.ts`) zeigt nur die Blöcke bis zum aktuellen/zuletzt trainierten (Arbeitswochen + „Deload“), ab Block 2 gruppiert.
- Muskel-IDs (22): chest, upperBack, lats, biceps, triceps, frontDelts, sideDelts, lowerBack, abs, traps, rearDelts, forearms, obliques, neck, serratus, quads, glutes, hamstrings, calves, abductors, adductors, tibialis. Frühere IDs `shoulders`/`core` werden beim DB-Upgrade (Dexie v2) und Backup-Import migriert. Nur auf Wunsch (Fokus "Höher") plant der Generator: forearms, neck, serratus, tibialis, obliques, lowerBack.
- Neue Übungen: Zeile in `data/exercises.ts` ergänzen, Anleitung in `data/instr/*` (Test prüft Vollständigkeit). Tests prüfen eindeutige IDs/Namen und Mindestabdeckung pro Muskel.
- Schemaänderungen an Dexie: neue `this.version(n)` ergänzen, alte nie ändern. Backup-Format (`exportAll`) mitpflegen.
- UI-Texte auf Deutsch, Design über CSS-Variablen in `index.css` (Hell/Dunkel).
- Keine Secrets, kein Backend, keine externen Netzwerkaufrufe. Alle Daten bleiben lokal.

## Bekannte Grenzen / Offen
- Kein direkter Apple-Health/Health-Connect-Zugriff (Web-App): nur Datei-Import. Automatik erst mit Capacitor-Wrapper.
- App-Icons sind Platzhalter (`public/favicon.svg`), Deployment/Hosting steht aus.
- Progressions-Konstanten (Inkremente, Volumen, Rep-Ranges) sind Heuristiken, anpassbar in `engine/`.
- Backup-Import und Übungstausch im Wizard wurden bisher nicht automatisiert getestet.
